# Decision log

Durable, cross-chat decisions for the CashKaro Search prototype. **Read this at
the start of any session** so you don't re-litigate a settled question or rebuild
something the wrong way — that wastes tokens and ships wrong code.

Several chats work on this repo at once (two were editing it simultaneously on
2026-07-28). This file plus [MAP.md](MAP.md) is the only thing they share.

## How to use this file

- **Before deciding anything durable** (a convention, a pattern, a "we do X not
  Y", a rejected approach, a known trade-off) — check here first. If it's
  answered, follow it.
- **After a decision is made** in a chat — append an entry immediately, past
  tense, with the *why*. The why is what stops the next chat re-arguing it.
- Newest at the top of each section. **Never delete or rewrite another chat's
  entry**; if one is reversed, add a new entry and note "supersedes Dnn".
- Keep entries short. Link code with relative paths, Figma with node ids.
- Nothing here is aspirational — every entry describes what the code does today.

Entry format:

```
### Dnn — <one-line decision>  ·  <YYYY-MM-DD>
**Decision:** what we do.
**Why:** the reason (so it isn't re-argued).
**Applies to:** files/surfaces, or "all".
```

## Context system

### D016 — Context lives in three files; two are generated/checked, none are optional · 2026-07-28
**Decision:** [MAP.md](MAP.md) answers *where* (generated by
[scripts/gen-map.mjs](../scripts/gen-map.mjs) from doc headers + the import
graph — never hand-edited), this file answers *why*, and
[CHANGELOG.md](CHANGELOG.md) narrates *when*. [../CLAUDE.md](../CLAUDE.md) is the
session bootstrap and [../AGENTS.md](../AGENTS.md) holds the hard rules. A
PostToolUse hook regenerates the map after every Write/Edit and a Stop hook runs
[scripts/check-context.mjs](../scripts/check-context.mjs), which reports stale
context, undocumented modules and hard-rule violations.
**Why:** parallel chats only know what these files say. Generating the map means
it cannot drift; checking it at the end of a turn means the reminder arrives while
the work is still in context, not on the next session's clock.
**Applies to:** all.

### D015 — The tokens-only rule exempts the web preview harness · 2026-07-28
**Decision:** `check-context.mjs` enforces "no colour literals outside
[theme/tokens.ts](../src/theme/tokens.ts)" for app UI, and exempts `src/os/*`,
[src/Root.tsx](../src/Root.tsx) and [ScreenNav.tsx](../src/components/ScreenNav.tsx)
(the device frame, mock status/nav chrome and the preview sidebar), plus
`src/data/*` where brand tints are brand data.
**Why:** the harness paints the *browser preview* around the app and never ships
inside it; holding it to the design-system palette would add tokens that mean
nothing to the product. Blanket enforcement that everyone ignores is worse than a
narrow rule that stays true. The remaining app-side violations the checker reports
are real drift, not exemptions.
**Applies to:** scripts/check-context.mjs, src/os/, src/Root.tsx, ScreenNav.tsx.

### D073 — Vertical measurements need REAL time; `--virtual-time-budget` freezes entering animations · 2026-07-29
**Decision:** when measuring a rect that sits under a Reanimated `entering`
animation (`FadeInDown` on the SERP hero, and every staggered card), do NOT read
it from a `--dump-dom` run driven by `--virtual-time-budget`. Reanimated's web
entering animations are CSS keyframes, which the compositor does not advance under
virtual time — the element stays frozen part-way through its translate and every
vertical number is wrong (the hero's 16px gap measured 34–36 three runs running,
and held steady long enough to look settled). Instead: delay the `load` event with
a slow subresource, run the probe from `DOMContentLoaded`, poll `getBoundingClientRect`
until the value repeats, and have the page write the result into a fixed overlay
that a plain real-time `--screenshot` then captures. Horizontal numbers are safe
either way — a vertical translate doesn't move them, which is why the 20px
alignment readings in D071 stood.
**Why:** three consecutive probe runs reported a gap 18px larger than the code
implied and stayed stable across samples, which reads exactly like a real layout
bug — the temptation is to "fix" the padding until the number matches, breaking
the real layout.
**Applies to:** any measurement of `src/components/SerpShell.tsx` rows,
`StoreHero`, or any animated card.

### D014 — Layout bugs are verified by measuring the DOM, not by eyeballing a screenshot · 2026-07-28
**Decision:** to prove a layout fix on web: `npx expo export -p web --output-dir
dist-<name>`, inject a probe script into the built `index.html` that walks the DOM
and prints each scroller's `getBoundingClientRect()` + `scrollWidth`, serve it,
then `Google Chrome --headless=new --virtual-time-budget=6000 --dump-dom`. Compare
numbers before/after. Delete the build dir afterwards.
**Why:** the full-bleed fix (D013) looked "sort of right" in screenshots; the
measurement showed the exact 20px shortfall (rail viewport ended at x=885 inside a
frame whose content ran to 905) and proved every rail was fixed afterwards.
Chrome's minimum window width is ~500px, so narrow-viewport screenshots also lie —
a 430px window renders a 500px viewport and crops it, which reads as a layout bug
that doesn't exist.
**Applies to:** any layout/clipping work.

### D012 — Preview builds are never committed · 2026-07-28
**Decision:** `dist-*/` is gitignored. Export previews to `dist-<purpose>/` and
delete them when done.
**Why:** a mid-session commit swept a temporary `dist-serp/` preview build into
git (157 files) along with a `Root.tsx` that was temporarily seeded to boot
straight into a SERP for screenshotting. Both were reverted; the ignore rule stops
the first from recurring, and D011 stops the second.
**Applies to:** .gitignore, any `expo export` run.

### D011 — Never leave test seeds in Root state; restore before ending the turn · 2026-07-28
**Decision:** to screenshot a deep screen, temporarily seed the controller state
in [src/Root.tsx](../src/Root.tsx) (`active`, `committed`, `mode`, `g`,
`viewAllCat`, `viewAllKey`), then restore it in the same turn. Back up the file
first and diff against `HEAD` before restoring — another chat may have edited it
meanwhile.
**Why:** there is no deep link into a screen, so seeding is the only way to render
one headlessly. It got committed once (D012). A blind `cp` of a stale backup also
reverted another chat's `raiseKeyboard()` refactor, which had to be restored by
hand.
**Applies to:** src/Root.tsx.

## Product photography

### D038 — Product images are studio shots on a white ground; the amateur ones get replaced, not cropped · 2026-07-28
**Decision:** every `assets/products/*` image should be a studio product shot on a
white ground, matching the style of the supplied
`iphone-15-pro` render. Audit the folder with
[scripts/check-product-photos.mjs](../scripts/check-product-photos.mjs) (share of
near-white pixels per file) and confirm by eye with a contact sheet — an HTML grid
of `file://` images screenshotted by headless Chrome with
`--allow-file-access-from-files`. Replaced so far: `iphone-15-pro` (supplied
AVIF, converted to 1000px JPEG), `iphone-15` and `apple-watch` (studio renders
from the merchant listing, vsprod.vijaysales.com).
**Why:** the original set came from Wikimedia Commons, which is why several were
phones photographed on a grey desk — they read as a different product class next
to the studio renders around them. The metric alone can't decide: white margins
had been padded around some desk photos (so a border sample called them clean),
and a tight studio crop that fills the frame scores *low* (`iphone-15-pro` reads
19.6%). Hence probe-then-look, and hence replace rather than crop — cropping a
desk photo still leaves a desk.
**Still amateur, no clean source found:** `mattress` (Wakefit — wakefit.co and
Pepperfry both 403 to a fetch), `raw-chicken` (Licious — no image URL in the
fetched page), `phone-stand` / `phone-tripod` (ELV accessories; the only shots are
in-situ, and substituting another brand's render would misrepresent the product).
Drop a file in `~/Downloads` and it can be installed the same way.
**Applies to:** assets/products/, data/realData.ts `PRODUCT_IMG`.

## Store cards & brand data

### D010 — Store cards render ONLY the 44 brands in the Figma Storepage tile set · 2026-07-28
**Decision:** [src/data/storeTiles.ts](../src/data/storeTiles.ts) is the single
source for every store card: the 44 unique brands from Figma "Storepage Tiles"
(`qDyQsqusZTtdGdBPdua6QT`, node 611:3360 — 15 rows × 3, Croma twice), each with
that frame's own logo PNG (`assets/brands/figma/`), its sampled wash, its offer
strip and its cashback figure/caption. Every surface goes through it — SERP stores
rail, category grids, View-all, Home + Explore Top Stores. Catalog store slots map
onto tiles via `storeTileSlots()` (stable per slug, distinct within a rail).
**Why:** the previous cards drew logos from a favicon CDN, which rendered blurry
and off-brand (the reported "invented logos"). The design defines the exact brand
set; pinning cards to it makes fidelity structural instead of a review step.
**Applies to:** all store-card surfaces.

### D009 — The search index stays unfiltered, so a card may show a different brand than the query · 2026-07-28
**Decision:** `STORES`/`PRODUCTS` in [catalog.ts](../src/data/catalog.ts) keep
every brand (Flipkart, Myntra, Apple, boAt …) and search behaves exactly as
before. Only the *cards* are restricted to the Figma set (D010). Searching "flip"
therefore shows a Flipkart hero with Croma/Amazon/AJIO tiles beneath it.
**Why:** explicit founder call — "keep the search stuff same, just change the
brand cards to these ones, even if we have to show wrong cards in search."
Replacing the catalog would have deleted the demo queries the prototype exists to
show.
**Applies to:** src/data/catalog.ts, src/data/storeTiles.ts.

### D008 — Figma logos are extracted per logo node, then background-stripped by border flood-fill · 2026-07-28
**Decision:** for each tile, call the Figma MCP `download_assets` on the *logo*
node (the child of the tile's `Frame 1991635403`) and keep the largest raw image —
not a render of the tile. Then make the background transparent by flooding
near-white (≥244) inward **from the border only**, and trim to the alpha bbox.
Verify on a tinted background before shipping.
**Why:** per-node raw images are the designer's own files at full resolution, so
nothing is re-drawn or approximated. A global white→alpha threshold would punch
holes in reversed type (the white "HDFC BANK" wordmark inside its blue block);
flooding from the border only preserves enclosed whites. Logos with a baked white
box read as white rectangles on a tinted wash — the exact artefact this avoids.
**Applies to:** assets/brands/figma/, any future Figma logo export.

### D007 — Storepage tile values are transcribed, not derived · 2026-07-28
**Decision:** each tile's wash, offer strip ("Upto 80% Off", "Rates from 9.99%",
"Zero Foreclosure", "100% Digital"), cashback figure and footer caption
(CASHBACK vs REWARDS) come from the frame verbatim. Rows 1–12 share the neutral
wash `#eef2fb` → `color.aura.tileWash`; rows 13–15 carry real brand tints, which
live in `storeTiles.ts` as brand data. The contract gained
`Cashback.pct_single.prefix` (for "Flat 1%") and `ResultItem.cashbackCaption`
(for "REWARDS") so the card renders the design instead of a near-miss approximation.
**Why:** the per-category `CATEGORY_OFFER` fallback it replaced invented a
discount ceiling per category — a value with no source. Tile-supplied strings
can't drift from the design.
**Applies to:** src/data/storeTiles.ts, src/data/dataContract.ts, StoreTile.

### D006 — `StoreTile` uses `heroTint` as an exact wash and softens only a legacy `logoBg` · 2026-07-28
**Decision:** when an item carries `heroTint`, `StoreTile` paints it verbatim
(gradient tint → transparent). `softTintRgb(…, 0.8)` now applies only to items
that arrive with just a brand `logoBg`.
**Why:** the design's washes are already final pale values; whitening them 80%
flattened every tile to near-white. Keeping the old path means non-tile store
items still render sensibly.
**Applies to:** src/components/ResultCards.tsx → StoreTile.

## The production-app home clone

### D035 — The home banner page is FULL width; the 16px inset belongs to the artwork · 2026-07-28
**Decision:** the banner rail's scroll frame, page width and snap step are all one
integer equal to the **full** screen width; the 16px gap is
`paddingHorizontal: 16` on each page, so the artwork is `W − 32`. Height is
`(W − 32) / 1.6649746192893402`. Each page also carries its own explicit
`{ width }` — without it the page sizes to the artwork's intrinsic width and paging
drifts. **Supersedes the geometry sentence in D029**, which read fn #19974's two
`Dimensions.get('window')` calls as "a `W` frame inside a `W − 32` centred wrapper".
**Why:** that reading put the inset on the *frame*, so it began 16px in and ran 16px
past the right screen edge — the reported "banners clipping", and exactly the bug
AGENTS.md §Paged carousels describes. The height dividing `W − 32` is the tell: the
height matches the **artwork's** width, not the page's. Measured after the fix
(D014): frame left 0, width 520, `scrollWidth` 1560 = 3 × 520, each page 520 with
its image at left 16 and width 488.
**Applies to:** HomeScreen.tsx `HomeBanners`; any future clone of an app carousel.

### D034 — Home uses THIS prototype's search bar, not the app's copied field · 2026-07-28
**Decision:** Home keeps the app's search **band** (absolute, `top` = the toolbar's
40, `SEARCH_HEIGHT_DEFAULT` 64 tall) but renders nothing in it. `Root.tsx` hoists
the one live [SearchBar](../src/components/SearchBar.tsx) and rests it there —
`REST_Y` is now **40**, and the opacity fade added by D030 is gone, so the bar is
visible at rest again. The app's own field (`searchInputWrp`, its `CkSearchIcon`,
and the "Search for products/brands/deals" cycler) was deleted from HomeScreen.
**Supersedes D030.**
**Why:** explicit request — *"match the new search bar in this home as well, we will
use the new search bar in this home."* It also lands cleanly: the prototype's bar is
exactly 64 tall (`paddingVertical: 8` + a 48 field + 8), the same as the app's
reserved band, and it is opaque, so it doubles as the band's white backing. One bar
across every surface also keeps the Home → Search glide a true shared element
instead of a crossfade between two different fields.
**Applies to:** HomeScreen.tsx, Root.tsx.

### D027 — Home is copied out of the shipped app binary, not redrawn from a screenshot · 2026-07-28
**Decision:** [src/screens/HomeScreen.tsx](../src/screens/HomeScreen.tsx) is a clone
of the **production CashKaro app** home, two scrolls deep. Every colour, size,
weight, gap and nesting order in it was decompiled out of
`/Applications/CashKaro.app/Wrapper/CashKaro.app/main.jsbundle` (Hermes bytecode
v96) with [hermes-dec](https://github.com/P1sec/hermes-dec) — the person asked
explicitly for "only the exact code from the app, don't build anything from
screenshots", and macOS Screen Recording was not granted to the host process
anyway, so screenshots were not an option. Each extracted value carries its Metro
module or function id in a comment, so any of it can be re-derived:
`Home` #19765 · `renderHomePageSections` #19876 · `HomeToolbar` #20001 ·
`Banner` #19974 · `HomeBannerPaginationItem` #19990 · `HomeTitleSection` #20115 ·
`CategoryCard` #20141 · `TopCategoryHorizontal` · `StoreCard` #20200 ·
`<Text>` #12439 · `MenuIcon` #20014 · `BottomTabNavigator` #5882 ·
colours module **897** · utility StyleSheet + Metropolis map module **896** ·
`CONTAINER_HEIGHT_DEFAULT`/`SEARCH_HEIGHT_DEFAULT` module **1693**.
**Why:** "exact same design" is only checkable if each number has a provenance.
Re-deriving from a screenshot would have invented spacing and colour.
**Applies to:** HomeScreen.tsx, theme/ckApp.ts, icons/ckAppIcons.tsx.

### D028 — The app's design system lives in theme/ckApp.ts, NOT in tokens.ts · 2026-07-28
**Decision:** the app's own system — `colors` (module 897, 40 roles),
`base` (module 896's 204 utility styles: `ph16`, `rowHCenter`, `rounded8` …),
`metropolis` (nine weights, five vendored), `text` (the `xs`/`sm`/`md`/`lg`/`xl`
→ 10/14, 12/16, 14/20, 16/24, 18/24 scale) and `metrics` — sits in
[src/theme/ckApp.ts](../src/theme/ckApp.ts). `tokens.ts` is untouched.
**Why:** `tokens.ts` is the Figma-sourced **search** design system; ckApp.ts is the
shipped **app** design system. They disagree on type family (Outfit vs Metropolis)
and on greys, so merging them would corrupt both. `theme/` is exempt from the
no-hex rule in `check-context.mjs`, so the literals are legal exactly here.
**Applies to:** theme/ckApp.ts vs theme/tokens.ts; anything cloning app surfaces.

### D029 — Three knowing deviations from the app, each flagged at its call site · 2026-07-28
**Decision:** (1) the banner rail is a paged `ScrollView`, not
`react-native-reanimated-carousel` — same widths (`W` frame inside a `W−32`
centred wrapper), same height (`(W−32)/1.6649746192893402`), same
`autoPlayInterval` 3000; (2) the five bottom-tab glyphs come from this repo's
icon set because the app's are separate SVG assets that were not extracted — the
bar's labels, tints (`secondary` active, `black` inactive), `52 + insets.bottom`
height and 10px Metropolis-SemiBold label ARE the app's; (3) the store-card CTA's
`borderRadius` is 8 because the app passes it as a Button prop we did not resolve,
and 8 is the app's own `base.rounded8` used by every other card edge on Home.
Section *content* is server-driven in the app, so it comes from this repo's real
data with the app's own copy strings ("Top categories", "Highest Cashback Stores",
"Exclusive Offers"). The pre/post-exit float is behind `SHOW_PRE_POST_FLOAT`
(default false) because the app only shows it when returning from a store.
**Why:** an unflagged approximation reads as extracted fact to the next chat.
**Applies to:** HomeScreen.tsx.

### D030 — The hoisted search bar rests at 52 and is invisible on Home · 2026-07-28
**Decision:** [src/Root.tsx](../src/Root.tsx) `REST_Y` moved 64 → **52** (the app's
toolbar height 40 + the search block's `paddingTop` 12) and `barStyle` now
interpolates opacity `0 → 1` over the first 0.15 of the gesture.
**Why:** Home paints the production app's own search field (part of the copied
design), so the shared bar would have stacked a second bar on top of it. Fading it
in from the same Y keeps the Home → Search handoff reading as one element.
**Applies to:** Root.tsx, HomeScreen.tsx.

## Layout

### D075 — The AI band's air sits under the sheet edge, not above it · 2026-07-29
**Decision:** [ExpandSearch](../src/components/ExpandSearch.tsx)'s band `marginTop`
goes back to `space.m` (16, from 40 — superseding the `+24` in commit 8bfa427),
and the clearance from the sheet's curved edge down to the band's first line of
text goes from 12 to `SHEET_CLEAR` = `space.s12 + space.xl` (44). The same
constant is used by both the pitch and the results heading, so the heading does
not shift against that edge when the pitch settles into results.
**Why:** the two gaps stack into one uninterrupted white column — 40 of page
background, then the 40px white sheet end — so the deals carousel appeared to
float a long way from anything while the AI copy sat tight under the curve,
reading as the sheet's last line rather than the AI surface's first. Moving the
air from above the band to below the curve closes the deals section up and puts
the separation where it does semantic work. Total height barely moves (92 → 100);
what changes is which element the space belongs to.
**Applies to:** components/ExpandSearch.tsx.

### D074 — The new-user chip's gift glyph is solid; the icon map stays regular · 2026-07-29
**Decision:** the welcome-bonus chip in [StoreHero](../src/components/ResultCards.tsx)
renders `<Icon name="gift" weight="solid" size={10} …>`. `ICON.gift` in
[iconMap.ts](../src/icons/iconMap.ts) is unchanged (`regular`).
**Why:** designer call — at 10px an outline gift is a few hairlines on a pale green
field and reads as a smudge rather than a gift. Fixed at the call site rather than in
the map because the map's other consumer is the Home clone's bottom tab bar, where
`gift` sits at 18px beside four other outline tabs (home, rupee, search, user) — a
solid glyph there would break a row that is pixel-matched to the production app. This
is what `Icon`'s `weight` prop is for; the map still owns *which glyph*, the call site
owns *how heavy* when the size demands it. Verified on the built page: the chip's
glyph computes `font-family: FA6Pro-Solid` at U+F06B, and both bundled faces carry
that code point (checked with fontTools, so the change can't silently render tofu).
**Applies to:** the one `Icon` in `StoreHero`'s `isNew` chip. Not a general rule that
small icons go solid — no other call site changed.

### D077 — The deals rail's glow may not spill DOWNWARD, and the AI band sits 8px under it · 2026-07-29
**Decision:** `dealGlow`'s bottom reach drops from `-space.huge` (64) to
`-space.s` (8) — the other three sides keep their spill — and
[ExpandSearch](../src/components/ExpandSearch.tsx)'s `band` marginTop goes 16 → 8.
**Why:** the band paints an opaque white sheet directly under the deals section,
so the half of the glow that spilled below the rail was covered rather than seen,
ending the bloom in a hard horizontal line (the "glow is clipping from the bottom"
report). Pulling the bed in lets the ramp reach zero above that edge, so there is
nothing left to cut. The gap change is the same problem from the other side: the
band's own sheet-end curve already reads as air below the deals, so an outer 16px
on top of it stacked into ~60px of dead white between the pagination dots and the
aura. Supersedes the 16 recorded on the band (itself superseding a +24).
**Applies to:** components/ResultCards.tsx `dealGlow`, components/ExpandSearch.tsx `band`.

### D076 — Web-search cards name the merchant in a muted footer; catalog cards don't · 2026-07-29
**Decision:** `ResultItem` gains an optional `retailer { name, logo }`, set ONLY
by [webResults.ts](../src/data/webResults.ts). `ProductCard` renders it as the
card's last row — hairline rule, 14px mark, `caption10Medium` in `priceMuted`,
reading "on Amazon". The merchant is chosen per product by the same stable hash
the feed already uses, from a category → merchant map whose values are
`storeTiles.ts` keys only, so the mark is the same Figma asset the store cards
use and no off-design brand can reach the screen (AGENTS.md).
**Why:** a Google-Shopping result's shop is the one fact a catalog card doesn't
imply, and the grid mixes shops. Driving it off a contract field rather than a
component flag keeps it off the SERP product rails and category pages, which
share `ProductCard` and would otherwise all grow a footer. It is the quietest row
on the card by design — the brief was "balanced and non-intrusive".
**Applies to:** data/dataContract.ts (`retailer`), data/webResults.ts,
components/ResultCards.tsx `ProductCard`.

### D072 — `BrandThumb` takes a `scale`, and the store hero's logo runs at 0.65 · 2026-07-29
**Decision:** [BrandThumb](../src/components/ImageSlot.tsx) gained an optional
`scale` (default 1) that shrinks the logo inside the tile without touching the
tile; `StoreHero`'s 88×60 thumb passes `scale={0.65}` (first shipped at 0.5, then
taken up 30% on review). Every other BrandThumb
(store rows, suggestions, finance cards) is unchanged.
**Why:** designer call on the Myntra hero. The symbol-only assets (D066) are
cropped tight to their ink box, so at the tile's default 0.96×0.86 they reach its
edges where a lockup would have left air. A prop on the shared component keeps
the change to the one call site that wanted it.
**Applies to:** ImageSlot.tsx `BrandThumb`, ResultCards.tsx `StoreHero`.

### D071 — In bleed mode the hero has no padding of its own; the page's 20px is the only inset · 2026-07-29
**Decision:** `heroBleed` (ResultCards.tsx) drops the hero's `padding: space.m`
for a `paddingTop` of `space.s` (8) only — no horizontal padding — so logo, title,
figure, chip, CTA and timeline strip all inherit the page column's `space.m20` and
sit at 20px like every other row. The "Cashback Timelines" label's 4px nudge is
zeroed in bleed mode too. Measured on the built page (D014/D073) at 500px: context
line, "Up to", timelines label, CTA box and brand tile all land on `left: 20`, and
the context line's bottom → logo-tile top gap is 16.00 (the context row carries
8px of its own bottom padding, so the hero adds only the other 8). The boxed
(Gallery) variant keeps its 16px card padding.
**Why:** the 16px hero padding was measured from a card edge. With the card gone
it stacked on the page's 20 and pushed the whole hero to 36px — every hero row
sat 16px right of the context line above it and the section heads below.
**Applies to:** ResultCards.tsx `StoreHero` bleed mode.

### D070 — The hero CTA follows the Store Page V2.0 sticky-button spec, and hero percentages carry 2 decimals · 2026-07-29
**Decision:** [StoreHero](../src/components/ResultCards.tsx)'s CTA reads
"Earn Cashback on {Store}" for every store with cashback (both user types;
`ctaLabel`/"Visit Store" stays the no-cashback fallback), set in 16/SemiBold with
a 12px solid arrow-up-right at gap 4 (Figma 1716:74837/74840) on the CK Orange
`aura.ctaHero` fill, under a looping soft-light `Shine` sweep. The bundled
FA6Pro subset has no `arrow-up-right` (e09f), so iconMap's `earn` maps to
`arrow-up` (f062) and the call site rotates it 45° — the identical shape. Hero
cashback *percentages* (big figure + "Up from" chip) always show 2 decimals
("6.00%"); flat ₹ keeps Indian grouping with no decimals, because the formatter
can't group and round at once without inventing paise.
**Why:** designer-supplied screenshot + Figma spec for the store money page; the
per-store CTA names the earn action, and 2-decimal rates match the production
app's money formatting.
**Applies to:** ResultCards.tsx `StoreHero`, [motion/Shine.tsx](../src/motion/Shine.tsx),
[icons/iconMap.ts](../src/icons/iconMap.ts).

### D069 — Store-hero SERPs paint a full-bleed HeroBleed backdrop, mounted above the status bar · 2026-07-29
**Decision:** the store hero's wash/orbs no longer live in a rounded card. A
non-scrolling [HeroBleed](../src/components/HeroBleed.tsx) layer (wash gradient +
brand-tinted Aura orbs + a 300px white dissolve, 620 tall) is mounted by
[Root](../src/Root.tsx) as the **first child of the app column — above the mock
status bar, outside `stageBody`** — so one gradient runs from the device's

### D086 — Trending is TWO looping rails that drift, not a wrapping row · 2026-07-29
**Decision:** the trending pills move into `motion/LoopRail.tsx` — a horizontal
scroller whose children are laid out three times, parked in the middle copy, with
the offset normalised into `[W, 2W)` on every tick. `ExploreHome` deals the pills
into two rails (greedy by label length, so the rows balance) drifting opposite ways
at ONE speed, ±10 px/s — only the direction differs, so the pair reads as one
mechanism counter-rotating rather than as two loosely related rows. Gutters are `space.s12` (12) on both axes; the rails are
full-bleed (`bleed={space.m20}`) and carry no content padding, so pills run off both
edges the way a marquee should. Drift is a plain `requestAnimationFrame` loop
writing `scrollTo`; a drag pauses it and hands back its end position.
**Why:** seven pills at 44px tall wrapped to four rows once the disc landed (D081),
and the brief was two lines at any pill count — a rail does that where a wrapping
row cannot. Three copies rather than two is what makes a manual drag endless in
BOTH directions: with two, dragging back stops at offset 0, because RN has no
content to the left of it. Normalising by a full copy width is invisible precisely
because the pixel under the finger is identical. rAF rather than a Reanimated
worklet: `scrollTo` in a worklet is a native-only path and this rail has to move in
the web preview too — the same reasoning that keeps count-ups on rAF (D068). At
10px/s a frame moves a sixth of a pixel, so the loop costs one imperative call per
frame and nothing else.
**Copy count is derived, not fixed at three:** `Math.ceil(vw / W) + 3`. A scroller
clamps at `content − viewport`, so with three copies a set narrower than the
viewport puts offset 2W *past the end* — and a rail drifting RIGHT, which wraps to
2W on its very first tick, sits pinned there looking frozen. That is exactly how the
second rail presented ("bottom line is not moving"): the top rail drifts up from W
and never reaches the clamp, so only the reversed one showed it.
**Applies to:** motion/LoopRail.tsx, screens/ExploreHome.tsx (`trendingRows`, the
Trending block, the `chips` gutter). Reduced motion arms no frame loop — the rails
stay ordinary scrollers.
**Verified:** web export at real elapsed time (see D081 on holding the load event
open): row 1's content moved ~200px LEFT between 6s and 26s, row 2's the same
distance RIGHT (measured while row 2 still ran at −8; the magnitudes were equalised
after), gutters measured 12, and all 21 mounted discs (7 pills × 3 copies)
carried both reel frames with the visible layer at opacity 1 — the three that read
static are the savings pill, whose reel is a single illustration.

`listening → hearing → settling`, and words are revealed **only while `voiced` is
true**, so the transcript stalls the moment you stop talking.
**Why:** a voice affordance that floats over the page reads as a modal; taking the
keyboard's slot reads as the keyboard *becoming* a microphone, and keeps the field in
view. Feeding the visual from shared values keeps the meter on the UI thread — React
state is touched only by the 8Hz word/silence poll, which is all speech needs.
**Applies to:** VoiceSheet.tsx, useVoiceLevel.ts, Root.tsx, SearchBar.tsx (`onVoice`).

### D045 — The voice sheet has no speech recognition, and says so on screen · 2026-07-28
**Decision:** the transcript comes from a `PHRASES` list in VoiceSheet.tsx, revealed in
time with real voice activity. The **meter is genuine; the words are not.** The sheet
prints "live mic" or "demo signal" so nobody demoing it can mistake which. Swapping in
a real STT engine means replacing `PHRASES` with its partial results — no other change.
Two behaviours worth keeping if that swap happens: the mic-permission race
(`MIC_GRANT_TIMEOUT` 900ms → fall back to the synth, because a prompt the person
ignores otherwise leaves a dead meter — and a headless browser never resolves it at
all), and finalising a **complete** utterance on the first breath instead of waiting out
`SILENCE_MS` (the meter's slow release keeps `level` above the gate for most of a
natural pause, so the silence window never fired).
**Why:** a showcase surface that looks like working recognition must be labelled as one,
in the code and on the screen. Both caveats above were found by measurement, not
guessed — the first froze the meter, the second froze the sheet in "Listening…".
**Applies to:** VoiceSheet.tsx, useVoiceLevel.ts.



### D036 — The deals rail glows in its current banner's colour, and that colour is sampled from the artwork · 2026-07-28
**Decision:** `DealsCarousel` renders ONE static centred glow behind the pager and
its indicator — `centredGlowFill(item.bannerTint)`, an ellipse on `farthest-side`
whose ramp is compressed into the inner 78% of its box and closed with a
zero-alpha stop at the edge. No clock, no orbs, no drift. Peak alpha is 0.95 and
the glow bed is deliberately LARGER than the section (`-space.xl` sides,
`-space.l` top and bottom). `bannerTint` is a new `ResultItem` field carrying the creative's
dominant field colour, produced by
[scripts/sample-banner-tint.mjs](../scripts/sample-banner-tint.mjs) —
`count × sqrt(saturation)` over a coarse RGB histogram, ignoring buckets under 2%
of the image. The glow layer is keyed on the tint so React crossfades it over
`duration.slow` as pages advance — the colour is the only thing that moves.
**Why:** static because it sits *behind* the artwork — a drifting field there
pulls the eye off the deal, which is what the first pass did. Compressed into 78%
of the box because a full-width ramp met the section's top and bottom edges and
cut in a straight line; fading to nothing inside its own box means no `overflow`
setting can clip it, however short the section is (measured: zero pixel change
between banner changes, and clean white above and below the rail).
"changes colour according to banner colour" can't come from the brand
palette — the Amazon creative's field is pale blue, not Amazon orange — and RN
can't read image pixels at runtime without another dependency. Sampling offline
keeps it exact and free at runtime, and matches how the store-tile washes were
derived (D008). The scoring details are load-bearing: plain `count × saturation`
picked the small intense red temple out of a light-blue banner, and unweighted
count returns the white page ground. Note the deal *labels* in `realData` don't
all match their artwork (`deal-klook` renders the S3 Beauty creative) — the tint
travels with the asset, so the glow matches what is on screen regardless.
Near-opaque peak and an oversized bed because the deal banner is a PNG with its
own baked white ground: it covers the glow's bright middle, so the only part that
ever reaches the eye is the outer half of the ramp in the thin margin around the
artwork. At a "tasteful" 0.5 peak inside a section-sized bed that margin landed
around 5% alpha and read as nothing — the reported "can't even see the glow".
Spilling past the section lets the bloom read in the page around the deal instead.
**Applies to:** components/ResultCards.tsx `DealsCarousel`, data/realData.ts
`ALL_DEALS`, dataContract `bannerTint`, scripts/sample-banner-tint.mjs.

### D035 — Never judge Reanimated motion from a `--virtual-time-budget` screenshot · 2026-07-28
**Decision:** to prove an animation runs, measure two **real-time** frames from
the Simulator (`xcrun simctl io booted screenshot`, ~2s apart) and diff the
pixels — `scratchpad/pngdiff.mjs` (node zlib only) prints mean-abs-diff and the
percentage of pixels changed. Headless Chrome with `--virtual-time-budget` is
still correct for *layout* (D014) but useless for motion.
**Why:** virtual time does not advance Reanimated's clock, so every frame you
capture is the same frame. Two separate animation drivers (`useFrameCallback` and
`withRepeat(withTiming)`) both measured as **exactly zero motion** on web while
both measured 7–13 mean-diff on device. Before this was understood, motion was
reported as "verified" off two web screenshots that differed for unrelated reasons
(a phase change, a banner autoplay) — the aura had in fact been drifting so slowly,
and in a hue so close to its own wash, that it read as a static gradient.
**Applies to:** any motion claim; scratchpad/pngdiff.mjs.

### D034 — Orb softness is an eight-stop alpha ramp, and the AI ramp carries six hues · 2026-07-28
**Decision:** orbs are painted with `SOFT_RAMP` — alpha `1 → .82 → .52 → .26 →
.1 → .02 → 0` reaching zero at 92% of the box — five of them at peak alpha
0.34→0.20, `AI_ORB_SIZE` 320, on a 16s master loop with amplitudes 58–82px.
`AI_FLOW_HUES` is now cobalt → indigo → violet → orchid → magenta → aqua (still
cyclic), and `AI_ORB_HUES` gives each orb its own hue from that ramp. The mark is
a **3D asset** (Fluent Emoji sparkles, MIT, `assets/icons3d/`) on a radial glow
platter, not a glyph on a gradient tile. The band drops its bottom hairline and
carries `space.m + space.xxl` of bottom padding, and `SerpShell` omits its
trailing spacer when the band is present, so the field runs off the screen bottom.
**Why:** a linear falloff has a findable edge, so the orbs read as discs — "very
distracting" was the report, and the fix is the alpha *shape*, not a blur filter
(which iOS won't run anyway, D017). Four hues read as a purple gradient; six
including magenta and aqua read as magical, which is the brief. A full-colour 3D
render fights a saturated gradient square, hence the glow platter. Icons8's own 3D
sets return `countAll: 0` on the anonymous MCP tier, so the 3D asset came from a
licence-clean source instead of being faked from a 2D glyph.
**Applies to:** motion/Aura.tsx, components/ExpandSearch.tsx, components/SerpShell.tsx,
tokens (`aiMagenta`, `aiAqua`, `AI_ORB_HUES`, `aiGlow*`), assets/icons3d/.

### D033 — The store hero runs the same Aura field, tinted from the brand, and dissolves into the page · 2026-07-28
**Decision:** `StoreHero` layers `AuraField` (from [motion/Aura.tsx](../src/motion/Aura.tsx))
over its existing brand wash with `base={false}` and `fills={brandOrbFills(item.heroTint)}`,
so the drifting orbs glow in that store's own colour — `tintRgba()` reads the
brand tint's RGB and applies the orb's own alpha (0.34 / 0.24 / 0.18), ignoring
whatever alpha the tint carries. The panel's bottom is a
`fade0 → surface` gradient (`space.huge96` tall) rendered **under** the content,
with `paddingBottom: space.xl` to give it room.
**Why:** one engine, one clock, one set of orbit maths for every ambient surface —
the AI band and the store hero differ only in palette. Deriving the hue from the
tint means a new brand needs no new tokens. The bottom fade exists because
`overflow: hidden` cuts the orbs off in a straight line at the panel's edge, which
is exactly the hard seam the panel was trying not to have; fading wash and orbs to
page white before the edge removes it, and keeping the fade below the content stops
it veiling the white timeline cells.
**Applies to:** ResultCards.tsx `StoreHero`, motion/Aura.tsx (`AuraField` gained
`fills` + `base`; new `tintRgba`, `brandOrbFills`), `color.aura.fade0`.

### D018 — `sparkle` in the icon map is a broom; AI surfaces use `ai` · 2026-07-28
**Decision:** render the AI mark and any "sparkle" affordance with
`Icon name="ai"` (FA `e2ca` wand-magic-sparkles). Do not use `name="sparkle"`.
**Why:** verified in the built web bundle at 3× zoom — `e5d1` resolves to
**broom-wide** in the bundled FA6 Pro subset, and real `fa-sparkles` (`f890`) is
not in the subset at all (renders blank in Regular, Solid and Light). The map's
`// sparkles` comment is wrong, not the font. Left the map entry alone rather than
repointing a shared file mid-session: [components/UserTypeToggle.tsx](../src/components/UserTypeToggle.tsx)
still shows a broom on "New User" and wants either `ai` or a re-subset font
including `f890`.
**Applies to:** icons/iconMap.ts consumers; ExpandSearch.tsx, UserTypeToggle.tsx.

### D017 — AI surfaces flow from one display-linked clock, and their softness is a real radial gradient — never a blur filter · 2026-07-28
**Decision:** the Aura engine ([src/motion/Aura.tsx](../src/motion/Aura.tsx)) owns
every AI gradient. One `useFrameCallback` clock (`t`, wrapped to a 24 s master
loop, plus a `rate` multiplier) drives all layers on the UI thread; each layer
samples it with sin/cos at **integer harmonics** of that loop, so paths are
Lissajous (organic, not a visible back-and-forth) and the composite is seamless
when the clock wraps. Glow orbs are `radial-gradient` fills — structured
`experimental_backgroundImage` on native, the equivalent CSS on web (`radialFill`)
— and every falloff ends on a **zero-alpha stop of its own hue**. A flowing fill
is a strip `SPAN × width` wide carrying the cyclic hue ramp `REPEATS` times, so it
translates one pattern period forever with no reset (`FlowStrip`). Phase changes
animate `rate`, never restart an animation.
**Why:** the old card used `filter: blur(34px)` behind `Platform.OS === 'web'`, so
on device the "soft wash" was two hard-edged gradient circles — RN only wires
`filter: blur()` to iOS behind the off-by-default `enableSwiftUIBasedFilters`
flag, and an offscreen blur pass per frame is what drops ProMotion frames anyway.
`withRepeat` keyframes also can't be retimed mid-flight without a seam, and a
`p > 0 && p < 1 ? 0.5 : 0` shine slab reads as a hard diagonal band, not as light
(visible in the reported screenshot). Fading to `transparent` interpolates through
grey and leaves a dirty ring, hence the same-hue zero-alpha stops. Period is
`1.5 × width`, not `1 × width`, so matching hues never sit at both ends and the
fill reads as travelling in one direction.
**Applies to:** motion/Aura.tsx, components/ExpandSearch.tsx, `color.aura.ai*` +
`AI_*` tokens.

## Search routing

### D052 — Finance-vertical words resolve to that vertical's results page, ahead of the catalog · 2026-07-28
**Decision:** query resolution in [Root.tsx](../src/Root.tsx) is now
`REAL_CASES[key]` → `financeSerp(key)` → `buildSerp(query)`. `financeSerp`
([data/realData.ts](../src/data/realData.ts)) word-boundary matches `/\bloans?\b/`
→ `caseLoans` and `/\bcards?\b/` → `caseCards`, two broad cases that REUSE
`caseAmountLoan`'s and `caseCredit`'s own sections (same item objects — every rate,
EMI and fee stays single-sourced) and re-label only the context line: "3 personal
loans · ranked by rate (low → high)", "3 credit cards · ranked by CashKaro reward".
They are deliberately NOT in `REAL_CASES`, so intent has exactly one router.
**Why:** "loans" and "cards" are category-level searches with nothing in the
catalog to match — `buildSerp` returned undefined and the prototype answered the
two biggest BFSI queries with the recovery screen. Routing them through the
amount-specific case instead would have headed a broad query with "Lowest EMI for
₹5,00,000", and reusing `caseCredit` verbatim would have echoed "for “credit”"
above a search for "cards". Exact keys in `REAL_CASES` still win, so "sbi cashback
card" keeps its resolved-card page, "credit" its cards SERP and "₹5,00,000 personal
loan" its amount page. The word boundary is what keeps this off store and product
names — no searchable name or keyword in `catalog.ts` contains "card" or "loan".
**Applies to:** Root.tsx (`model` memo, preview nav), data/realData.ts
(`caseLoans`, `caseCards`, `financeSerp`).

### D026 — Bottom sheets are the app's only modal surface · 2026-07-28

### D024 — `productCategories()` is a lazy memo, never a module-scope const · 2026-07-28

### D022 — Every number on a category page is derived; a page needs ≥3 products · 2026-07-28

**Why:** §7 (D005) — a browse page is exactly where invented "20+ results" numbers

**Applies to:** productCategories.ts, ProductCategory.tsx, the suggestions

## Pre-existing conventions (recorded 2026-07-28 from code + AGENTS.md, not invented)

### D005 — Un-sourced numbers are loudly flagged, never quietly plausible · pre-existing
**Decision:** values with no real source carry the greppable `PLACEHOLDER`
marker and render in `color.placeholder` / `placeholderSurface` (deliberately
garish). Loan APRs and savings rates are the only remaining placeholders.
**Why:** a prototype that shows invented figures as real is worse than one that
shows them as obviously fake.
**Applies to:** src/data/realData.ts, src/theme/tokens.ts.

### D004 — No component invents content; everything renders from the data contract · pre-existing
**Decision:** components take `ResultItem` / `SerpModel`
([dataContract.ts](../src/data/dataContract.ts)) — 13 archetypes. No component
hardcodes a name, rate, price or fee string. Real cases are transcribed in
[realData.ts](../src/data/realData.ts); anything else is generated from the
catalog by `buildSerp()`.
**Why:** one shape per result type means a new case is data, not a new component.
**Applies to:** all.

### D003 — A product card never falls back to a brand logo as its image · pre-existing
**Decision:** every catalog product has a real photo (`PRODUCT_IMG`); when one is
missing the card shows a neutral photo slot with a tag glyph.
**Why:** a logo standing in for a product photo reads as a bug and misrepresents
the SKU. Commits `271b3cd`, `edd15c2`.
**Applies to:** src/components/ResultCards.tsx → ProductCard.

### D002 — Figma values are pulled through the MCP and resolved to tokens · pre-existing
**Decision:** pull the real spec (`get_design_context`, `get_variable_defs`,
`get_metadata`, `get_screenshot`) — never eyeball a screenshot. Every hex/px/font
must resolve to a token in [tokens.ts](../src/theme/tokens.ts); if a needed value
is missing, add it there (palette + semantic role) rather than inlining a literal.
**Why:** eliminates colour/spacing drift and hallucinated values.
**Applies to:** all design → code work.

### D001 — Expo SDK 57; read the versioned docs before writing code · pre-existing
**Decision:** the project targets Expo SDK 57 (`expo ~57.0.6`, `react-native
0.86.0`, `react 19.2.3`). Confirm APIs against
https://docs.expo.dev/versions/v57.0.0/ before use.
**Why:** Expo's API surface moves fast; guessing produces code that fails at
runtime in a way typechecking won't catch.
**Applies to:** all.
